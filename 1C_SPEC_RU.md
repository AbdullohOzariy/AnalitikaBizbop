# Отправка данных из 1С в аналитическую платформу

Документ для разработчиков 1С. Приёмник **готов и работает** — можно начинать отправку.

---

## 1. Куда отправлять

```http
POST https://analitika.oilagroup.uz/api/1c/ingest
Content-Type: application/json; charset=utf-8
Authorization: Bearer <ТОКЕН>
```

Токен передаётся отдельно (не по открытому каналу). Если в 1С удобнее — вместо
`Authorization` можно использовать заголовок `X-Ingest-Token` с тем же значением.

**Проверка связи** (ничего не сохраняет):

```http
GET https://analitika.oilagroup.uz/api/1c/ingest
Authorization: Bearer <ТОКЕН>
```

Ответ `200` — связь есть. Ответ `404` — токен неверный.

## 2. Формат чека

Присланный вами образец (`analitic (1).json`) **принимается как есть** — менять
структуру не нужно. Ниже он же, для фиксации контракта:

```jsonc
{
  "shop": 5,                    // магазин  ← обязательно
  "pos": 1,                     // касса    ← обязательно
  "number": "121",              // номер чека ← обязательно
  "session": 1,                 // смена
  "openDate": "04.08.26",       // дата     ← обязательно
  "openTime": "16:49:04",       // время
  "type": 1,
  "status": "success",
  "fiscal": "",
  "barcode": "12345",           // штрихкод ЧЕКА
  "card": "1234567890",         // карта лояльности
  "user": { "id": 1, "name": "Системный администратор" },
  "payments": [
    { "name": "Наличные", "value": 68.68 }
  ],
  "positions": [
    {
      "item": {
        "id": 123,              // КОД НОМЕНКЛАТУРЫ ← по нему связываем с нашей базой
        "art": "A123",
        "name": "Стейк шейки свиной",
        "class_code": "ГТД 12345",
        "package_code": "Certificate1"
      },
      "barcode": "46057921",    // штрихкод НОМЕНКЛАТУРЫ
      "qty": 0.723,
      "storno": 0,
      "sum": 339.09,
      "sumR": 0,
      "sumWD": 249.49,
      "sumWT": 34.23,
      "totalSum": 249.49
    }
  ],
  "qtyBuys": 4,
  "qtyPositions": 3,
  "sum": 2839.09,
  "sumWithDiscs": 2728.92,
  "totalSum": 2728.92
}
```

**Пакетная отправка** — если удобнее слать не по одному:

```jsonc
{ "events": [ {чек}, {чек}, ... ] }     // либо просто массив: [ {чек}, ... ]
```

## 3. Что уже учтено на нашей стороне

| | |
|---|---|
| **Кодировка** | Понимаем и UTF-8, и **windows-1251** — распознаём автоматически |
| **Повторная отправка** | Безопасна. Дубля не будет: ключ `shop + pos + дата + number + session` |
| **Исправленный чек** | Если пришлёте тот же чек с изменёнными строками — они **перезапишутся** |
| **Неизвестные поля** | Сохраняются как есть, ничего не теряется |
| **Магазин не сопоставлен** | Чек всё равно сохранится; привяжем позже вручную |

## 4. Коды ответа

| Код | Значение | Что делать в 1С |
|---|---|---|
| `200` | Записано (ответ: `accepted` / `duplicates`) | Пометить как выгруженное |
| `400` | Тело не JSON | Ошибка формата — **не повторять** |
| `404` | Токен неверный | Проверить токен |
| `413` | Слишком большой пакет | Уменьшить порцию |
| `500` | Ошибка на нашей стороне | **Повторить позже** — дубля не будет |

Пример успешного ответа:

```json
{ "ok": true, "batchId": "…", "received": 3, "accepted": 3, "duplicates": 0 }
```

**Ограничения:** до 1000 чеков в одном запросе, тело до 8 МБ.

## 5. Что нужно от вас

### 5.1 Обязательно — без этого цифры будут неверными

**а) Кодировка.** Просим `UTF-8`. Мы поддерживаем и cp1251, но первый ваш
образец пришёл с **уже разрушенной** кириллицей (символы `?`) — восстановить
невозможно. Если так уйдёт хотя бы один чек, мы навсегда потеряем название
товара, ФИО кассира и **вид оплаты**.

**б) Итоги не сходятся.** В образце:

| Проверка | Сумма по строкам | В шапке | Расхождение |
|---|---|---|---|
| `sum` | 5 839.09 | 2 839.09 | 3 000.00 |
| `totalSum` | 5 749.49 | 2 728.92 | 3 020.57 |
| `payments` | 68.68 | 2 728.92 | 2 660.24 |

Также `sumWT = 34.23` одинаково во всех трёх строках с разной ценой,
а `qtyBuys = 4` при сумме `qty = 3.723`.

Нужна **формула каждого поля**: `sum`, `sumWithDiscs`, `totalSum`, `sumR`,
`sumWD`, `sumWT`, `qtyBuys`. Либо согласованный образец, где всё сходится.

**в) Соответствие магазинов.** `shop: 5` — какой это объект? Нужен список для
всех точек: Mega Center, Gold Mart, Oila SM, Smart City (Учкудук), кафе,
Mazzona, игровые зоны.

**г) Виды оплаты.** Полный список возможных значений `payments[].name`
(наличные / карта / перечисление / сертификат / …). По ним мы раскладываем
выручку на наличные и безналичные.

### 5.2 Желательно

- **`Ref_Key` (GUID) чека.** Сейчас защита от дублей построена на связке
  `shop + pos + дата + number + session`. Если такой GUID есть — пришлите,
  будет надёжнее.
- **Дата в ISO с зоной**: `"2026-08-04T16:49:04+05:00"` вместо `"04.08.26"`.
  Сейчас читаем как время Asia/Tashkent.
- **Значения полей:** `type` (1 — продажа? возврат?), `session`, `status`
  (кроме `"success"`), `aos`, `fiscal` (когда заполняется).
- **Возвраты:** отдельный чек или флаг `storno` в позиции?
- **Режим отправки:** сразу при пробитии или пакетом? Ожидаемый объём в сутки?
- **Очередь при недоступности.** Если наш сервер временно недоступен —
  есть ли повтор? (`500` можно повторять безопасно.)

## 6. Документы — отдельный формат

Чеки и документы храним **раздельно**. Для документов ждём образцы:

- `Поступление товаров` (приход)
- `Перемещение товаров`
- `Списание товаров`
- `Возврат поставщику`
- `Инвентаризация`
- `Установка цен`

⚠️ **Важно:** в текущем формате нет поля, по которому можно понять **тип
документа**. Поле `type: 1` — это тип чека, а не вид документа. Просим в каждом
документе передавать его тип строкой, например:

```jsonc
{ "kind": "ПоступлениеТоваровУслуг", "shop": 5, "number": "…", ... }
```

Иначе приход и чек будет невозможно различить.
